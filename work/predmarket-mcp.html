predmarket-mcp: live prediction-market data as tools for AI agents

Kalshi and Polymarket price thousands of real-world questions, from Fed decisions to recessions. But their APIs differ in almost every way: units, order-book conventions, search, history. This MCP server hides all of that behind six clean tools, so an agent like Claude can search, quote and compare both venues in plain language.

Engineering problems worth solving

1. Two venues, one language

Kalshi quotes dollars as strings and keeps separate YES and NO books; Polymarket uses token IDs per outcome and JSON-encoded arrays. Every price leaves the server as a YES probability between 0 and 1. A Kalshi NO bid at p becomes a YES ask at 1 − p, and a Polymarket fill on the NO token is converted the same way. Volume keeps its native unit (contracts vs. USD) and is always labeled, never mixed.

2. Search where the API has none

Kalshi's documented API has no keyword search. My first version paged through every open event (50+ requests) and built an inverted index, which worked but made a cold search take about 10 seconds and could trip Kalshi's rate limit. The server now uses the public search endpoint behind kalshi.com's own search box: one request, about 0.3 seconds, quotes included. Because that endpoint isn't documented, any failure falls back automatically to the index, built from documented endpoints and cached for 10 minutes.

3. Built for agent traffic

Agents call tools in bursts and often repeat themselves. Requests are spaced evenly per venue instead of burst-then-backoff; 429s and 5xx retry with exponential backoff and honor Retry-After; and a TTL cache collapses identical in-flight requests into one upstream call. A 15-topic comparison sweep makes 30 upstream requests with zero rate-limit errors.

4. Cross-venue matching that doesn't fall for look-alikes

Two markets can share most of their words and still be different bets. The first version paired a Kalshi "Fed funds above 3.50%" market with a Polymarket "3.0%" market and reported a 98-point "gap", which would badly mislead an agent. So before scoring, every pair must pass checks built from real title pairs, each with a regression test:

CheckRejected look-alike
Same thresholds"above 3.50%" vs "3.0%"
Same comparison"above 3.75%" vs "exactly 3.75%"; "more than 25bps" vs "25 bps"
Close vs touch"Bitcoin above $150k on Dec 31" vs "Bitcoin reaches $150k in 2026"
Same direction"cut by 25bps" vs "increase by 25 bps"
Same negation"Fed cuts 1 time" vs "no Fed cuts"
Shared action, not just names"Who will dissent at the FOMC? (Powell)" vs "Powell out from the Fed Board"

Pairs that pass are scored by word overlap weighted by rarity ("Fed" and "2026" count less than "dissent" or "shutdown"), checked for close dates within 45 days, and matched one-to-one. Genuine pairs now line up closely, as they should:

compare_venues("fed hike")   # live, Nov 2026
gap  -0.020  Kalshi: exactly 1 Fed rate hike in 2026?   Polymarket: 1 Fed rate hike in 2026?
gap  -0.004  Kalshi: exactly 3 Fed rate hikes in 2026?  Polymarket: 3 Fed rate hikes in 2026?
gap   0.000  Kalshi: hike by 25bps in December?         Polymarket: increase by 25 bps in December?

A gap still isn't automatically an arbitrage. Kalshi's 2027 recession market resolves on an NBER call, for example, and Polymarket's has its own rules and cut-off. The server's instructions tell the agent to check resolution rules before treating any gap as an opportunity.

Quality

  • 31 tests with mocked HTTP (respx): parsing, unit conversion, order-book sorting, retries, caching, search fallback, and matching regressions from real title pairs. No network needed.
  • Tested end-to-end over the real MCP protocol: launch the server over stdio, list the tools, call them against live data.
  • GitHub Actions CI on Python 3.12 and 3.13, with ruff lint and format checks.
  • Every tool is marked read-only, and inputs are clamped to safe ranges.
